# Architecture

The application uses Next.js App Router under `app/`. Shared UI lives in `components/`, product requests in `services/`, browser demo state in providers and `lib/`, and static editorial material in `data/` where applicable. Fake Store API is the primary source for product records. Account and purchase data are simulated in the browser and do not represent a backend account or a charged order.

The API Studio route exercises the remaining public sample resources through `services/demoApiService.ts`. Product requests stay in `services/productService.ts`. The Studio discards returned password fields and login tokens, does not store entered sample passwords, and keeps simulated API writes separate from the storefront's browser cart and demo orders.

The resource workbenches at `/products/manage`, `/carts`, and `/account/users/manage` reuse the same service layer. `/carts/explore` and `/carts/[id]` read public sample carts and enrich product IDs through the shared product service; copying a sample cart updates only the existing local browser cart. `/account/users` reads sanitized public users into a client-side table, where filters and pagination do not request or store passwords. It requires the browser demo session and redirects anonymous visitors to login. The sample API login validates public credentials against `/auth/login`, discards its token, looks up a sanitized public user record, and establishes a browser-only demo session. This session is for presentation and is not server authorization. User write forms send only fictional example data and never collect a personal password.

The current architecture retains legacy route and component locations to keep the project usable during incremental refactoring. Server rendering is preferred for content that does not need browser state; client providers own cart, wishlist, theme, and demo session interactions. Catalog filtering and cart pricing live in pure modules under `lib/` and have unit tests.
