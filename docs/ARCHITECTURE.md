# Architecture

The application uses Next.js App Router under `app/`. Shared UI lives in `components/`, product requests in `services/`, browser demo state in providers and `lib/`, and static editorial material in `data/` where applicable. Fake Store API is the primary source for product records. Account and purchase data are simulated in the browser and do not represent a backend account or a charged order.

The resource-specific demo routes exercise public sample resources through `services/demoApiService.ts`. Product requests stay in `services/productService.ts`. Public user data excludes password fields, sample login tokens and entered passwords are discarded, and simulated API writes stay separate from the storefront's browser cart and demo orders. The standalone API Studio route has been removed.

The resource workbenches at `/products/manage`, `/carts`, and `/account/users/manage` reuse the same service layer. `/carts/explore` and `/carts/[id]` read public sample carts and enrich product IDs through the shared product service; copying a sample cart updates only the existing local browser cart. `/account/users` reads sanitized public users into a client-side table, where filters and pagination do not request or store passwords. It requires the browser demo session and redirects anonymous visitors to login. The sample API login validates public credentials against `/auth/login`, discards its token, looks up a sanitized public user record, and establishes a browser-only demo session. This session is for presentation and is not server authorization. User write forms send only fictional example data and never collect a personal password.

Routes follow App Router conventions in `app/`, while components are grouped by feature and shared primitives remain in `components/ui/`. See [PROJECT-STRUCTURE.md](PROJECT-STRUCTURE.md) for the directory map. Server rendering is preferred for content that does not need browser state; client providers own cart, wishlist, theme, and demo session interactions. Browser storage failures leave in-memory demo interactions usable. Catalog filtering and cart pricing live in pure modules under `lib/` and have unit tests. The home and dedicated FAQ pages share one accurate content source in `data/faq.ts`.

Recovery UI is centralized in `components/feedback/`: App Router error boundaries offer a reset action, the root-layout fallback renders its own document shell, unknown routes show a 404 state, and data views distinguish request failures from empty results. The data-query retry action refetches in place; filter-driven empty states offer a reset where filters apply.
